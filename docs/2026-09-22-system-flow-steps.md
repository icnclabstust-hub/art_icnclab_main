## 1. 實作里程碑順序

**設計原則**：每個 Phase 都有明確的「進入條件」與「完成條件」。進入條件未滿足就開工，產出無法驗收。

```
P0 前置解卡（三項可並行）
  │  A1 指派 Annotator ──┐
  │  A4 確認法規告知文字 ─┼─→ A3 保存期限確認（18 週是否符合法規）
  │  A5 Approver 核可 ───┘
  ▼
Phase 3  對話記錄 + 召回率評測
  │  BIZ-02 pipe 傳身分 → EVL-01 建黃金集 → EVL-06 建基準 → 納入夜間流程
  ▼
Phase 4  證據、拒答與忠實度
  │  GRD-08 影子模式累積 → GRD-05 用黃金集校準門檻 → 分路由逐步啟用
  ▼
Phase 5  Router / 融合 / 重排
     RET-04 系統級 RRF → 量測 → 決定是否加重排與 Router 權重

另案（不阻擋主線，可獨立排程）：B10 Redis 快取、B11 嵌入版本標註、
B12 稽核寫 alerts、B13 Google Books（不做）、SYS-06-T 存取控制
```

### 1.1 Phase 0：前置解卡

| 步驟 | 動作 | 執行者 | 完成條件 |
|---|---|---|---|
| P0-1 | 指派黃金測試集標註人選 | 專案 | `Annotator` 角色有具名人員，且確認可投入 2–3 小時 `[EVL-02]` |
| P0-2 | 確認適用法規、告知文字，以及是否需研究倫理審查 | Approver（指導老師／學校資訊或法務） | 告知文字定稿；倫理審查需求有書面結論 `[BIZ-05]` |
| P0-3 | 依 P0-2 結論確認 `biz.messages` 保存期限 | Approver | 確認 18 週符合結論，或給出替代期限 `[BIZ-04]` |
| P0-4 | Approver 核可 Tier B 實作，補簽 GD 評估表 §九 | Approver | 核可有紀錄。**AI 不代填任何簽核欄** `[BIZ-06]` |
| P0-5 | 指派拒答佇列每週複審人選 | 專案 | `Reviewer` 角色有具名人員 `[EVL-16]` |
| P0-6 | 決定執行期目錄處理方式並執行（建議甲案） | Operator | 執行期目錄 `git remote` 指向正本 `[SYS-05-T]` |

> **P0-6 的必要性**：未完成前，所有程式碼變更都不會生效於實際運行的系統。若暫不執行甲案，流程 F 必須走「手動同步」分支，且每次變更都要重複一次。

**維運待辦並行執行**（不阻擋 Phase 3，但阻擋對應驗收）：
OPS-01 換 ES 密碼、OPS-02 確認 9/22 夜間實跑、OPS-03 開 PR、OPS-04 清 `.env`、OPS-05 `query_logs` 移出追蹤、OPS-07 ES 重啟迴圈檢定 OOM、OPS-08 埠號整併機器端套用。

### 1.2 Phase 3：對話記錄與召回率評測

**進入條件**：P0-1 ~ P0-5 全部完成（P0-4 核可是硬性前置）。

| 步驟 | 動作 | 完成條件 |
|---|---|---|
| 3-1 | `BIZ_LOGGING` 保持 **關閉** | 設定確認為 `false` `[BIZ-03]` |
| 3-2 | 修改 pipe，將使用者身分（或匿名代號）傳至後端 | 後端能取到 `user_id` `[BIZ-02]` |
| 3-3 | 建立 `eval.golden_set` 並完成標註 | 15 題全部標註完成 `[EVL-01～04]` |
| 3-4 | 實作四段量測，寫入 `eval.measurements` | 單次 run 產出四段指標 `[EVL-06～07]` |
| 3-5 | 以現況系統跑一次，取得**基準值** | 基準 run 存在且含 `commit_sha` `[NFR-06]` |
| 3-6 | 實作 `biz.messages` 保存期限與自動備份 | 逾期自動刪除、刪前備份 `[BIZ-04]` |
| 3-7 | 上線告知文字 | 首次使用顯示告知 `[BIZ-05]` |
| 3-8 | 開啟 `BIZ_LOGGING` | 對話記錄開始累積（不再是 0 筆） `[BIZ-01]` |
| 3-9 | 將量測納入夜間流程（流程 D） | 每日自動產出 run `[EVL-08]` |

**完成條件**：基準值存在、夜間自動量測運作、`biz.messages` 有資料且保存機制生效。

> **3-2 是 Phase 3 的真正第一步**。`biz` 表雖已建好，但 pipe 沒傳身分，不改這一段，3-6～3-8 全部量不到東西。

### 1.3 Phase 4：證據、拒答與忠實度

**進入條件**：Phase 3 完成（**必須有黃金集與基準值**，否則門檻無法校準）。

| 步驟 | 動作 | 完成條件 |
|---|---|---|
| 4-1 | 實作證據判定、模糊檢索補救、K 分數計算，全部設為**影子模式** | 只記錄不阻擋，回應行為不變 `[GRD-08]` |
| 4-2 | 累積影子資料（建議 ≥ 2 週或 ≥ 500 次查詢，取先到者） | `eval.measurements` 有 K 分數分布 |
| 4-3 | 以黃金集校準門檻，驗證 `K > 0.7` 是否為適當切點 | 有校準報告；必要時調整門檻值 `[GRD-05]` |
| 4-4 | 實作 `gate_error` 放行路徑與 1% 告警 | 注入異常回 200 帶標記，超標告警 `[GRD-09～10]` |
| 4-5 | 實作拒答佇列 | 拒答寫入 `eval.refusal_queue` `[GRD-04、EVL-15]` |
| 4-6 | 實作同步粗篩（≤ 300 ms）與非同步 LLM 判官精篩 | p95 達標；精篩結果入庫 `[GRD-06～07]` |
| 4-7 | **分路由逐步啟用**阻擋：先 `vector`，再 `fulltext`，最後 `graph` | 每啟用一路，量測一次，退步即回退 `[RET-03]` |

**完成條件**：拒答實際生效、拒答率落在可接受範圍、忠實度指標優於基準。

> **4-1 到 4-7 不可跳步**。直接啟用門檻而不先跑影子模式，等於用猜的數字決定拒答，會出現兩種錯誤都無法察覺：門檻太鬆（幻想照舊）或太嚴（能答的全拒）。

### 1.4 Phase 5：Router、融合與重排

**進入條件**：Phase 4 完成（防護生效後才有穩定的品質量測基礎）。

| 步驟 | 動作 | 完成條件 |
|---|---|---|
| 5-1 | 實作 Router（依請求指定策略，預設 `hybrid`） | 四種策略皆可指定 `[RET-01～02]` |
| 5-2 | 實作**系統級 RRF**（`k` 預設 60） | 融合後 recall@n 優於單路最佳 `[RET-04]` |
| 5-3 | 量測 RRF 效果 | 有對照數據：單路 vs 融合 `[RET-05]` |
| 5-4 | **依 5-3 結果**決定是否加入輕量重排（非 cross-encoder） | 加入後有量測證明改善，否則不加 `[RET-06]` |
| 5-5 | **依 5-3 結果**決定是否調整 Router 各路權重 | 同上 |

**完成條件**：RRF 上線且有量測支撐；重排與權重的取捨有數據依據而非預設。

## 2. 流程 A：每日資料更新（每日 03:00，自動）

**觸發**：Windows 工作排程器 → `Run-DailyCrawl.ps1` `[SYS-01]`

| A-4 | 前處理、切塊 | — |
| A-5 | **惡意內容掃描** | 命中則該文件不進 catalog，記錄並告警 |

**驗收（OPS-02）**：移除 Yale 後的第一次完整實跑須逐步確認，不可只看最終無錯誤訊息。

## 3. 流程 B：線上查詢

**目標狀態流程**（Phase 4／5 完成後）。標 ⚠️ 者為現況缺失。

```
使用者提問
   │
B-1  接收請求（question, strategy, top_k, top_n, user_id, shadow）   [§11.1]
   │
B-2  查快取 ──命中──→ 回傳（cache_hit: true）                      ⚠️ [RET-11]
   │ 未命中
B-3  Router 依 strategy 路由（預設 hybrid）                          ⚠️ [RET-01]
   │
B-4  多路並行檢索：Chroma 向量 / ES 全文 / Neo4j 圖，各取 top_k      ✅ 可用
   │  （只取 valid_to IS NULL 的 chunk）                             [DAT-20]
B-5  RRF 融合，取 top_n                                              ⚠️ [RET-04]
   │
B-6  輕量重排（若 5-4 決定啟用；非 cross-encoder）                   ⚠️ [RET-06]
   │
B-7  ★ 證據判定：top_n 是否有足夠支撐？                              ⚠️ [GRD-01]
   ├─ 足夠 ────────────────────────────────┐
   │ 不足                                   │
B-8  模糊檢索補救（ES fuzziness），算 K     │                        ⚠️ [GRD-03]
   │  K = 最佳模糊命中的正規化分數           │                        [GRD-02]
   ├─ K > 0.7 ─────────────────────────────┤
   │ K ≤ 0.7                                │
B-9  拒答：回 refused:true + reason         │                        ⚠️ [GRD-04]
   │  + k_score + attempted_strategies       │
   │  寫入 eval.refusal_queue（不進快取）    │                        [EVL-15、RET-13]
   └─→ 結束                                 │
                                            ▼
B-10 生成（Ollama 11434），產出答案 + citations[]                    ✅／⚠️ [GEN-02]
   │  citations[] 為空 → 退回 B-9 拒答                               [GEN-04]
B-11 同步忠實度粗篩（≤ 300 ms）                                      ⚠️ [GRD-06]
   │  逾時或元件出錯 → 放行並標 gate_error，寫 eval.alerts            [GRD-09]
B-12 回傳答案 + citations + risk_flags + timings + cache_hit
   │
B-13 寫入快取（拒答不寫）                                            ⚠️ [RET-12～13]
B-14 寫入 biz.messages（BIZ_LOGGING=true 時）                        ⚠️ [BIZ-01～03]
B-15 非同步 LLM 判官精篩，結果寫 eval.measurements（不阻擋回應）      ⚠️ [GRD-07]
```

### 3.1 影子模式的行為差異 `[GRD-08]`

`shadow: true` 時，B-7～B-9 **只計算與記錄，不阻擋**：即使判定應拒答，仍繼續走 B-10 生成並回傳，同時把「本來會拒答」寫入量測。這是 Phase 4 步驟 4-1～4-3 的資料來源。

### 3.2 現況與目標的差距（一句話）

> 現況是 `B-1 → B-4 → B-10 → B-12`：**沒有 B-2、B-3、B-5、B-6，也沒有任何 B-7～B-9 的門檻**，因此任何檢索結果都會生成答案。

## 4. 流程 C：黃金測試集建立與基準量測（一次性）

**執行者**：`Annotator`（標註）＋ Operator（量測）
**前置**：P0-1 完成、Phase 3 步驟 3-2 完成

| 步驟 | 動作 | 產出 |
|---|---|---|
| C-1 | 選定主題範圍：**巴洛克時期**（資料完整度最高，作為基準） | 題目範圍界定 `[EVL-01]` |
| C-2 | 出 15 題，涵蓋事實查詢、關係查詢（藝術家↔作品↔流派）、以及**應拒答**的題目 | 15 題清單 |
| C-3 | 每題以現況系統檢索出約 20 個候選文件 | 15 × 20 候選 |
| C-4 | 標註者逐題標記 `relevant_doc_ids[]`（**文件層級**，非 chunk 層級） | 相關性標註 `[EVL-05]` |
| C-5 | 每題寫出 `gold_answer_points[]`（答案應涵蓋的要點） | 忠實度評分依據 |
| C-6 | 寫入 `eval.golden_set`，含 `annotator`、`annotated_at` | 15 筆 `[EVL-03～04]` |
| C-7 | 對現況系統跑一次四段量測，記錄 `commit_sha` 與設定快照 | **基準 run** `[EVL-06～07]` |
| C-8 | 將基準值登記為回歸比較基準 | 流程 D 的比較對象 `[EVL-08]` |

**工時估計**：C-2～C-6 約 2–3 小時（簡報估值）。
**須包含應拒答題目的理由**：否則 Phase 4 的門檻校準只能看「該答的有沒有答」，看不到「不該答的有沒有擋住」，門檻會系統性偏鬆。

## 5. 流程 D：夜間回歸與告警（每日，附掛流程 A）

| 步驟 | 動作 | 判斷與處理 |
|---|---|---|
| D-1 | 流程 A 完成後，對黃金集跑四段量測 | 產出當日 run `[EVL-06]` |
| D-2 | 與基準值逐指標比較 | 任一指標退步 **> 5 個百分點** → 寫 `eval.alerts` `[EVL-08]` |
| D-3 | 計算當日 `gate_error` 比例 | > **1%** → 寫 `eval.alerts` `[GRD-10]` |
| D-4 | 收集流程 A 的一致性稽核結果 | 不一致 → 已於 A-11 寫入 alerts `[DAT-05]` |
| D-5 | 彙總 `eval.alerts` 未處理項目 | 輸出至夜間流程報告檔，並由 `verify-nightly.sh` 第 9 節呈現 `[EVL-12]` |
| D-6 | 若有 alert，通知 `Operator` | 進流程 G |

**四類告警都經 `eval.alerts` 單一出口** `[EVL-10、NFR-05]`：一致性不符、量測退步、`gate_error` 超標、服務異常。

## 6. 流程 E：拒答複審（每週）

**執行者**：`Reviewer`（前置：P0-5 完成）

| 步驟 | 動作 | 產出 |
|---|---|---|
| E-1 | 取出本週 `eval.refusal_queue` 全部項目（含問題、K 分數、已試策略） | 待審清單 `[EVL-15]` |
| E-2 | 逐筆判定為三類之一：<br>① 應拒答（判斷正確）<br>② 應可答（門檻過嚴）<br>③ 資料缺漏（知識庫沒有這份資料） | 分類結果 `[EVL-17]` |
| E-3 | 第 ② 類累積 | 達一定量即回頭調整 K 門檻，並重跑流程 C-7 驗證 `[GRD-05]` |
| E-4 | 第 ③ 類回饋至採集層 | 列為來源補充需求（如 OPS-06 的 V&A 缺關係） |
| E-5 | 第 ① 類抽樣加入黃金集的應拒答題 | 強化 C-2 的覆蓋 |
| E-6 | 記錄複審紀錄（誰、何時、各類筆數） | 每週一筆 `[EVL-16]` |

> **E-3 是唯一合法的門檻調整路徑**。不經流程 C 驗證就改門檻，會把「解決個案」變成「破壞整體」。

### 8.2 已確診徵狀對照表

| 徵狀 | 成因 | 處理 | 編號 |
|---|---|---|---|
| `systemctl` 查不到服務 | 專案服務不由 systemd 啟動，而由 `Start-Process wsl.exe` 拉起 | **不是故障**。查 Windows 程序，或直接執行 `Start-NativeServices.ps1` | SYS-03 |
| Neo4j 反覆啟動失敗、`already running (pid:…)` | 系統 `neo4j.service` 與專案實例互搶埠 | `sudo systemctl disable --now neo4j`（停用前確認 7687 無其他用途） | B1 |
| 7688／7475 上仍有服務在聽 | 舊 Neo4j 實例未停乾淨 | 停掉舊實例；`verify-nightly.sh` §3 保留這兩埠的檢查即為此用 | — |
| Elasticsearch 每 30 秒 Start→Stopped | 待確認，先檢定 OOM | 確認為 OOM 則釘死 heap `-Xms2g -Xmx2g` | B3／OPS-07 |
| Ollama 回傳空模型清單 | 佔埠實例沒有專案所需模型 | 在該實例 `ollama pull`；先用 `collect.sh` 查出佔用者身分 | B2 |
| ml-service 呼叫失敗 | 與 Open WebUI 搶 8080 | ml-service 遷 8002，**`ports.md` §3 列的 8 處引用點須全部同步改** | C1 |
| 服務無預警消失、隔天才復原 | 無 watchdog，只靠每日 03:00 排程 | 短期：手動執行 `Start-NativeServices.ps1`；長期：實作 SYS-04-T 監管 | B5 |
| 改了程式碼但系統行為沒變 | 執行期目錄與正本脫鉤 | 走流程 F-5 手動同步，或完成 P0-6 遷移 | A4 |
| 設定改了卻沒生效、也沒報錯 | `os.getenv("X","預設值")` 安靜使用錯誤預設值 | 實作 `required_env`，必要設定缺漏即啟動失敗 | C6／SYS-07-T |
| 圖檢索召回偏低（特定館藏） | V&A 157／302 件缺豐富關係 | 列為採集層補充需求 | OPS-06 |

### 8.3 告警處理

| 告警類型 | 處理路徑 |
|---|---|
| 一致性不符（A-11） | 以 catalog 為基準重放 outbox 事件（冪等，可安全重放） |
| 量測退步 > 5pp（D-2） | 比對兩次 run 的 `commit_sha` 與設定快照，定位是哪一段（四段量測即為此設計） |
| `gate_error` > 1%（D-3） | 查防護元件異常原因；期間答案品質不可信，須告知使用者 |
| 服務異常（SYS-04-T） | 流程 G |
| 嵌入模型混用（A-12） | 停止 ingest，全量重建向量後再恢復 |
