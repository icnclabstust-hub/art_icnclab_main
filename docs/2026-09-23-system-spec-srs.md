## 1. 系統概觀

### 1.1 目的

建立一套以藝術史館藏與文獻為知識來源的檢索增強生成（RAG）問答系統，要求：

1. **有據可查**：每個回答可追溯到具體來源 chunk 與館藏識別碼。
2. **不可幻想**：檢索支撐不足時**拒答**，而非生成看似合理的內容（GRD-01）。
3. **可量測**：回答品質以黃金測試集量化，退步可被夜間流程自動偵測並告警（EVL 系列）。

### 1.2 使用者角色

| 角色 | 代號 | 權責 | 對應需求 |
|---|---|---|---|
| 查詢者 | `Querent` | 透過 Open WebUI 或 API 提問 | RET、GEN |
| 標註者 | `Annotator` | 建立與維護黃金測試集（15 題 × 約 20 候選） | EVL-01 |
| 複審者 | `Reviewer` | 每週複審拒答佇列。**已指派：使用者本人（論文作者）** | EVL-15～17 |
| 維運者 | `Operator` | 執行夜間流程、處理告警、備份還原 | OPS 系列 |
| 核可者 | `Approver` | 核可 Tier B 實作、確認法規與告知文字 | BIZ-05、BIZ-06 |

## 4. 資料層規格（L2–L3）

### 4.1 一致性模型

| DAT-ID | 需求 | 規格 | 狀態 |
|---|---|---|---|
| DAT-01 | 唯一真相源 | PostgreSQL `catalog` 為文件與 chunk 的唯一真相源；Chroma／ES／Neo4j 皆為**衍生副本**，可由 catalog 完整重建 | ✅ |
| DAT-02 | 變更傳播 | 所有對三庫的寫入一律經 `outbox` 表；不允許直接寫下游庫 | ✅ |
| DAT-03 | 投遞語意 | 訂閱器保證**至少一次**投遞，且所有下游寫入為**冪等**（同一 outbox 事件重放不改變最終狀態） | ✅ |
| DAT-04 | 一致性驗證 | 11 個來源的三庫一致性驗證通過（文件數、chunk 數、向量數三方比對） | ✅ 已實跑 |
| DAT-05 | 週期性稽核 | 夜間 `ingest verify` 比對三庫；**偵測到不一致須寫入 `eval.alerts` 並告警** | ✅ |

### 4.2 各庫職責與規格

| DAT-ID | 庫 | 職責 | 關鍵規格 | 狀態 |
|---|---|---|---|---|
| DAT-10 | ChromaDB | 稠密向量檢索 | 每個 chunk 一個向量；metadata 須含 `doc_id`、`chunk_id`、`source`、`embedding_model`、`embedding_version` | ✅ |
| DAT-11 | Elasticsearch | 全文／關鍵字檢索與模糊檢索 | 支援中文分詞；提供 `fuzziness` 查詢供 GRD-03 使用 | ✅ |
| DAT-12 | Neo4j | 實體關係圖（藝術家、作品、時期、流派、館藏） | 節點唯一性約束；**五種原子操作**；軟到期（`valid_to`）；30 天保留後硬刪除；`Artist.sources` 由關係動態推導，不儲存冗餘欄 | ✅ |
| DAT-13 | Neo4j | 網路綁定 | 僅綁 `127.0.0.1`，不對外監聽 | ✅ |
| DAT-14 | Neo4j | 備份 | 定期備份並驗證可還原。**以每 10,000 筆為單位切分，每一份放入獨立資料夾** | ✅ 已驗證還原／⚠️ 分片規格待實作 |
| DAT-15 | 全庫 | 備份存放位置與保留期 | 全部備份統一存放於各自獨立的資料夾：Neo4j 每萬筆分片、PostgreSQL、以及 `biz.messages` 的 18 週歸檔（BIZ-04）。**保留期：永久，不自動清除** | ❌ |
| DAT-15a | 全庫 | 備份時間標示 | 每一份備份**必須標明產生時間**：①資料夾名稱含 `YYYY-MM-DD_HHMM`；②資料夾內 `manifest.json` 記錄 `created_at`（ISO-8601 含時區） | ❌ |
| DAT-16 | 全庫 | 分片命名與可還原性 | 每個分片資料夾自帶還原所需的中繼資料，**單一分片可獨立還原**。`manifest.json` 至少含：`created_at`、`source`、`range`、`row_count`、`schema_version`、`checksum` | ❌ |
| DAT-17 | 全庫 | 永久保留的容量管理 | 備份永不清除，容量**必然單調成長**。夜間流程須在每次備份後記錄剩餘空間；低於 **20%** 寫入 `eval.alerts`（warning），低於 **10%** 為 critical | ✅ |

## 附錄 A：規格工具鏈

本附錄說明如何以程式讀取與更新本規格。**規格本文的唯一真相源是本檔與 `docs/2026-09-23-system-flow-steps.md` 兩份 Markdown**；以下皆為環繞它們的工具。

### A.1 機器可讀版本：`docs/spec.json`

由 `scripts/spec-export.py` 自本書與流程步驟文件自動產生。**單向衍生，不得反向編輯**：

```
Markdown（唯一真相源） ──scripts/spec-export.py──▶ docs/spec.json（衍生物）
```

| 用途 | 指令 |
|---|---|
| 產生／更新 | `python3 scripts/spec-export.py` |
| 只驗證不寫檔 | `python3 scripts/spec-export.py --check` |
| 列出可開工／被擋住的項目 | `python3 scripts/spec-export.py --next` |

**內建一致性檢查**（本版實作的子集，見 `scripts/spec-export.py` 內註解說明哪些已完整實作）：

| 代號 | 檢查內容 |
|---|---|
| C1 | 需求編號是否重複 |
| C2 | 狀態欄的標記是否可判讀（僅限 ✅／⚠️／❌／⏸／TBD／~~刪除線~~） |
| C8 | 表格每一列的欄數是否等於表頭欄數 |
| C11 | 目錄是否與實際標題逐條對應 |

### A.2 更新路徑：`scripts/spec-update.py`

更新一律寫回 Markdown，不寫進 `spec.json`：

```
系統 ──spec-update.py──▶ Markdown（唯一真相源） ──spec-export.py──▶ spec.json
```

| 操作 | 指令 |
|---|---|
| 需求狀態轉換 | `--set GRD-09=done` |
| 步驟結案 | `--close P0-6 --why "…"` |
| 步驟復開 | `--reopen P0-6` |

**安全設計**：最小改動（只置換目標儲存格）；原子性（寫入後立即驗證，失敗即還原）；冪等；每次成功更新追加一筆到 `docs/spec-changelog.md`；可用 `--dry-run` 預覽。
