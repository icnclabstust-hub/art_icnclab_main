### 1.2 Phase 3：對話記錄與召回率評測

**進入條件**：**無統一進入條件**，逐步判定見下表「前置」欄。

**現況（2026-09-23）**：P0-1、P0-4、P0-5、P0-6 均已結案，P0-2／P0-3（生效條件）暫緩。因此——
- **評測半邊（3-1、3-3、3-4、3-5、3-9）完全解鎖，現在就能做完**，這是 Phase 4 的全部前置。
- **對話記錄半邊（3-6、3-7、3-8）停擺**：`BIZ_LOGGING` 鎖定 `false`，`biz.messages` 維持 0 筆。
- **3-2 降為低優先**：傳身分的唯一近期消費者是 3-8，該步既已鎖定，先做也沒有消費者。

| 步驟 | 動作 | 前置 | 完成條件 |
|---|---|---|---|
| 3-1 | `BIZ_LOGGING` 保持 **關閉** | 無 | 設定確認為 `false` `[BIZ-03]` |
| 3-2 | 修改 pipe，將使用者身分（或匿名代號）傳至後端 | 無 | 後端能取到 `user_id`。**低優先**：唯一近期消費者已鎖定，可延後至 P0-2 恢復時再做 `[BIZ-02]` |
| 3-3 | 建立 `eval.golden_set` 並完成標註 | P0-1 | 15 題全部標註完成（P0-1 已結案，`Annotator`＝使用者本人） `[EVL-01～04]` |
| 3-4 | 實作四段量測，寫入 `eval.measurements` | 無 | 單次 run 產出四段指標 `[EVL-06～07]` |
| 3-5 | 以現況系統跑一次，取得**基準值** | 3-3、3-4 | 基準 run 存在且含 `commit_sha` `[NFR-06]` |
| ⏸ 3-6 | 實作 `biz.messages` 保存期限與歸檔 | P0-2 | 逾期自資料庫移除、移除前歸檔。機制本身無前置，但 `BIZ_LOGGING` 鎖定關閉時無資料可適用，先做無效益 `[BIZ-04、DAT-15a]` |
| ⏸ 3-7 | 上線告知文字 | P0-2 | 首次使用顯示告知；文字採「18 週後自線上資料庫移除，歸檔留存」，不得寫成「刪除」 `[BIZ-05、BIZ-04b、§12 R2b]` |

| 3-9 | 將量測納入夜間流程（流程 D） | 3-4 | 每日自動產出 run `[EVL-08]` |

**完成條件（依現況調整）**：基準值存在、夜間自動量測運作。`biz.messages` 有資料一項**隨 P0-2 暫緩，不列入本階段完成條件**——否則 Phase 3 將永遠無法宣告完成，Phase 4 也跟著卡死，而 Phase 4 實際上並不需要對話記錄。

> **3-2 是 Phase 3 的真正第一步，而且現在就能做**。`biz` 表雖已建好，但 pipe 沒傳身分，不改這一段，3-6～3-8 全部量不到東西。因 `BIZ_LOGGING` 仍為關閉，此步不寫入任何對話資料，不需等 `Approver`。
>
> **P0-2 暫緩後，Phase 3 一分為二**：評測半邊（3-1、3-3、3-4、3-5、3-9）全部可做且已無任何前置；對話記錄半邊（3-6～3-8）停擺。
>
> **Phase 4 不受影響**。它的前置是黃金測試集與基準值（來自 `eval.*`），不是對話記錄（`biz.*`）。因此 P0-2 暫緩**不會**擋住 Phase 4／5。
>
> ⚠ **但 Phase 4 會帶出一個新路徑**：拒答佇列（EVL-15）儲存使用者提問原文，不經 `BIZ_LOGGING` 管控。P0-2 暫緩期間須遵守 **EVL-15a**——該表不得寫入 `user_id` 或任何可連結到個人的欄位，否則等於繞過自己設的閘門。

### 1.3 Phase 4：證據、拒答與忠實度

**進入條件**：Phase 3 完成（**必須有黃金集與基準值**，否則門檻無法校準）。

| 步驟 | 動作 | 前置 | 完成條件 |
|---|---|---|---|
| 4-1 | 實作證據判定、模糊檢索補救、K 分數計算，全部設為**影子模式** | 3-5、3-9 | 只記錄不阻擋，回應行為不變 `[GRD-08]` |
| 4-2 | 累積影子資料（建議 ≥ 2 週或 ≥ 500 次查詢，取先到者） | 4-1 | `eval.measurements` 有 K 分數分布 |
| 4-3 | 以黃金集校準門檻，驗證 `K > 0.7` 是否為適當切點 | 4-2 | 有校準報告；必要時調整門檻 `[GRD-05]` |
| 4-4 | 實作 `gate_error` **拒答**路徑與 1% critical 告警；`gate_hang` 與 `gate_crash` 分開記錄 | 4-3 | 注入異常回 `refused: true`，超標發 critical 告警；注入掛住驗證 30 秒中止 `[GRD-06c～06d、09～10、NFR-03]` |
| 4-5 | 實作拒答佇列 | 4-4 | 拒答寫入 `eval.refusal_queue` `[GRD-04、EVL-15]` |
| 4-6 | 實作同步粗篩（**無品質逾時**，僅 30 秒掛住保護）與非同步**專用 NLI 模型**精篩。**粗篩只做本地字面比對，不得呼叫模型** | 4-4 | 精篩結果入庫；粗篩耗時記入 `timings.guard` 供觀測。驗證逾 30 秒會中止並記 `gate_hang`；程式碼審查確認粗篩內無模型呼叫 `[GRD-06、GRD-06a、GRD-06b、GRD-06c、GRD-06d、GRD-07]` |
| 4-7 | **分路由逐步啟用**阻擋：先 `vector`，再 `fulltext`，最後 `graph` | 4-6 | 每啟用一路，量測一次，退步即回退 `[RET-03]` |

**完成條件**：拒答實際生效、拒答率落在可接受範圍、忠實度指標優於基準。

> **4-1 到 4-7 不可跳步**。直接啟用門檻而不先跑影子模式，等於用猜的數字決定拒答，會出現兩種錯誤都無法察覺：門檻太鬆（幻想照舊）或太嚴（能答的全拒）。
>
> ⚠ **本節多項具體數值（30 秒逾時上限、1% 告警門檻、GRD-09 拒答而非放行、精篩採 NLI 模型而非 LLM 判官）在本對話中沒有拍板紀錄**，是使用者 2026-09-23 指示「依文件內容繼續」後採信落地；細節見 `docs/decision-log.md` 2026-09-23「提供出處說明」條目。

**進入條件**：Phase 4 完成（防護生效後才有穩定的品質量測基礎）。

| 步驟 | 動作 | 前置 | 完成條件 |

### 3.1 影子模式的行為差異 `[GRD-08]`

`shadow: true` 時，**B-7～B-9 與 B-11 的 `gate_error` 皆只計算與記錄，不阻擋**：即使判定應拒答、或粗篩逾時出錯，仍繼續走 B-10／B-12 回傳，同時把「本來會拒答」寫入量測。這是 Phase 4 步驟 4-1～4-3 的資料來源。

> **B-11 仍須納入影子模式**：若影子期間就讓 `gate_error` 阻擋，將無法分辨「防護判定為不忠實」與「防護自己壞掉」兩種情況，4-3 的校準會混入雜訊。

### 3.2 現況與目標的差距（一句話）

> 現況是 `B-1 → B-4 → B-10 → B-12`：**沒有 B-2、B-3、B-5、B-6，也沒有任何 B-7～B-9 的門檻**，因此任何檢索結果都會生成答案。

### 8.1 通用入口

### 8.2 已知徵狀對照表

| 徵狀 | 成因 | 處理 |
|---|---|---|
| `systemctl` 查不到服務 | 專案服務不由 systemd 啟動，而由 `Start-Process wsl.exe` 拉起 | **不是故障**。查 Windows 程序，或直接執行 `Start-NativeServices.ps1` |
| Neo4j 反覆啟動失敗、`already running (pid:…)` | 系統 `neo4j.service` 與專案實例互搶埠 | `sudo systemctl disable --now neo4j`（確認 7687 無其他用途） |
| Ollama 回傳空模型清單 | 佔埠實例沒有專案所需模型 | 在該實例 `ollama pull` |
| 服務無預警消失、隔天才復原 | 無 watchdog，只靠每日 03:00 排程 | 短期：手動執行 `Start-NativeServices.ps1`；長期：實作 SYS-04-T 監管 |
| 查詢卡住約 30 秒後回拒答，alerts 記 `gate_hang` | 粗篩掛住，由 GRD-06c 硬上限中止 | 不是慢，是掛住：查粗篩的迴圈或 I/O 是否無界。**勿為此調高 30 秒** |
| 拒答且 alerts 記 `gate_crash` | 粗篩拋例外或下游不可用 | 看例外堆疊；與 `gate_hang` 成因不同，修法也不同 |

### 8.3 告警處理

| 告警類型 | 處理路徑 |
|---|---|
| 一致性不符（A-11） | 以 catalog 為基準重放 outbox 事件（冪等，可安全重放） |
| 量測退步 > 5pp（D-2） | 比對兩次 run 的 `commit_sha` 與設定快照，定位是哪一段 |
| `gate_error` > 1%（D-3，critical） | 防護元件故障期間查詢一律被拒（GRD-09），屬**可用性事故**：立即查修，並告知使用者服務暫時受限 |
| 服務異常（SYS-04-T） | 流程 G |
| 嵌入模型混用（A-12） | 停止 ingest，全量重建向量後再恢復 |
