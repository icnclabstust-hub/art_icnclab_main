## 1. 背景與問題

現在的後端**無論檢索到什麼都會生成答案**：`unified_rag_manager_v2.py` 沒有任何相似度門檻（搜尋 `threshold／min_score` 無結果），也沒有「資料不足」的判斷。後果是檢索不到相關資料時，模型會用自身參數知識回答，使用者看不出差別，對藝術史研究這類需要出處的服務風險最高。

對照架構圖右側的「證據判定 → 無檢索支撐／拒答 → 忠實度／安全守門員 → 模糊檢索」整條防護，**目前一項都沒有**（僅有離線評測腳本 `scripts/eval_step2_compute_metrics.py` 用 LLM 事後算忠實度）。

**誰會用**：使用實驗室系統的研究者（看到誠實的不確定，而不是自信的錯誤）；實驗室（用拒答／風險標記數據改進資料與檢索）。
**不做會怎樣**：系統對外開放更多使用者後，幻覺與誤導性回答直接成為可見的品質與信譽風險。

## 2. 目標與非目標

### 目標
1. **4a**：檢索後判斷證據「足夠／不足／模糊」；不足時走「無檢索支撐」分支（拒答或標示風險），不再默默生成。
2. **4b**：回答後做忠實度檢查——同步粗篩（低延遲、必經）＋非同步精篩（LLM 逐句判斷，結果標記與量測）。
3. **4c**：證據不足且查無資料時，嘗試模糊檢索；可信度夠才採用。
4. 每個判斷都留下可追溯記錄（`event_id`、`route_id`），並納入 Phase 3 的量測與告警（拒答率 >15%）。

### 非目標
Router 自動路由、系統級 RRF／Reranker 收斂（Phase 5）；Redis 語意快取（另案）。

## 4. 方案比較

### 4.1 證據判定（4a）
| | 方案 A：分數門檻（分路由校準） | 方案 B：LLM 判斷「資料是否足以回答」 | 方案 C：門檻為主，灰區才交 LLM |
|---|---|---|---|
| 延遲 | 幾乎 0 | 數秒（多一次生成） | 多數查詢 0，灰區數秒 |
| 可重現 | 是 | 否（隨模型與提示漂移） | 大致是 |
| 需要的資料 | Phase 3 黃金集校準 | 少 | 黃金集＋少量灰區標註 |
| 風險 | 校準前門檻是猜的；分數分布會隨資料成長漂移 | 慢、貴、自身可能幻覺 | 兩者的複雜度 |
| **建議** | **先做 A（影子模式）** | 不單獨採用 | A 上線穩定後，若灰區比例偏高再加 |

三態輸出對應架構圖：`sufficient`／`insufficient`／`ambiguous`。門檻參數依路由存放於設定檔，不寫死。

### 4.2 忠實度（4b）——沿用上位設計 §4.3 的方案 B（兩段式），本文件細化
- **同步粗篩（必經、目標 ≤ 300 ms）**：(1) 答案文字經掃描器規則檢查是否洩漏指令或異常字元；(2) 答案切句後，以 `bge-m3` 計算每句與檢索內容的最高相似度，低於門檻的句數比例過高即標記；未過 → 降級（見 §4.4）。
- **非同步精篩**：以 LLM 逐句判斷「是否被檢索內容支持」，結果寫入 `eval.measurements`（`post_generation`）並在 `biz.messages` 標記風險，供每週人工抽樣。

| 精篩用什麼判斷 | 方案 A：沿用 Ollama LLM 判官（建議先用） | 方案 B：專用 NLI 模型 |
|---|---|---|
| 依賴 | 無新增；重用 `eval_step2` 的提示與解析 | 需新增模型與函式庫，並做來源、授權、供應鏈評估（CLAUDE.md §4「網路範例」規則） |
| 準確度／速度 | 中／慢，但是非同步，不影響使用者 | 通常較準較快，需驗證對中文與藝術史文本的表現 |
| 建議 | 先做，用黃金集比較 | A 準確度不足時再評估 |

> **更正（2026-09-23）**：使用者已裁定採**方案 B（專用 NLI 模型）**，非本表原建議的「先用 LLM 判官」（決策 B4，見 `docs/2026-09-23-system-spec-srs.md` GRD-07）。上表比較過程保留存查，實作以此更正為準。

### 4.3 模糊檢索（4c）
| | 方案 A：確定性（詞典別名＋既有模糊查詢） | 方案 B：LLM 改寫查詢再檢索 |
|---|---|---|
| 特性 | 快、可重現，只擅長拼寫變體、譯名、別名 | 能處理語意改寫，但慢且可能改變原意 |
| **建議** | **先做 A** | 之後再議 |

**「可信度 K>0.7」語意未定**（圖面未說明）：我的提案是「K＝最佳模糊命中的正規化分數（0–1）」，且模糊命中**只允許在證據判定為不足時才觸發**，採用後視同證據足夠直接回答；K≤0.7 維持拒答。此定義**需與老師／圖面原作者確認**（見 §9）。

### 4.4 「無檢索支撐」時怎麼做（政策選擇）
| | 方案 A：直接拒答，附說明與可行建議 | 方案 B：以模型知識回答，但明確標示「無檢索依據，風險自負」 |
|---|---|---|
| 適合 | 研究、引用、需要出處的場景 | 一般閒聊、容許不確定 |
| 風險 | 使用者覺得系統「不會回答」 | 使用者忽略標示，仍把答案當事實 |
| **建議** | **預設方案 A**，並提供可設定開關（`NO_EVIDENCE_POLICY=refuse\|flagged_answer`）；由老師決定預設值 | |

> **更正（2026-09-23）**：預設方案 A（拒答）已確認為最終決定（決策 B1，見 GRD-01）；開關**改採 09-23 規格書的變數名 `REFUSE_ON_NO_EVIDENCE`（布林，預設 `true`）為準**，本文件的 `NO_EVIDENCE_POLICY` 命名不再使用，避免兩份文件對同一設定用不同鍵名。

## 5. 系統設計（草案）

### 5.1 流程
```
檢索 ─► 4a 證據判定 ──sufficient──► 生成 ─► 4b 同步粗篩 ──通過──► 回傳
                     │                       └─未過──► 降級（依 §4.4）
                     ├─ambiguous──► 生成並標 risk_flag=faithfulness_review
                     └─insufficient──► 4c 模糊檢索 ──K>0.7──► 視為足夠，回到「生成」
                                                  └─否──► 無檢索支撐（依 §4.4）
生成後 ─► 非同步：4b 精篩（LLM 逐句）→ eval.measurements(post_generation)、biz.messages 風險標記
```

### 5.2 介面與資料（草案，皆為新增）
- `/api/v1/query` 回應新增（上位設計 §5.3 已定）：`evidence_status`、`route_id`、`risk_flag`（`none｜faithfulness_review｜refused`）。
- `biz.messages` 新增：`evidence_status`、`risk_flag`。
- `eval.refusal_queue`（新表）：被拒答或低相似度的查詢抽樣，供每週人工判斷「是真的資料不存在，還是檢索失敗」；只存去識別化後的問題文字，適用 Phase 3 §6 的全部隱私規則。
- 設定檔：各路由的證據門檻、粗篩門檻、政策開關；**一律有預設值與影子模式**。

### 5.3 失敗與降級
- 任一防護元件本身出錯（例如嵌入服務逾時）：**不得靜默放行也不得讓整個服務失敗**——回答照常送出但標 `risk_flag=gate_error` 並記錄告警（此原則需老師確認，見 §9）。
- 精篩失敗：只影響量測與標記，不影響已送出的回答。

> **更正（2026-09-23）**：第一點的「放行並標 `gate_error`」**已被推翻**。使用者裁定改為**拒答**：防護元件出錯 → `refused: true`、`reason=gate_error`，已生成的答案丟棄，不得送出未經把關的內容；`risk_flags` 不再出現 `gate_error`（該值改走拒答回應，非風險標記）（決策 B3，見 GRD-09、GEN-03、NFR-03）。逾 30 秒掛住保護視為此類出錯的一種，記 `gate_hang`；例外／崩潰記 `gate_crash`（GRD-06c～06d）。

### 5.4 上線方式（降低對線上服務的衝擊）
1. **影子模式**：只計算並記錄 `evidence_status`／粗篩結果，不改變回答；累積資料。
2. **校準**：用 Phase 3 黃金集與影子資料訂門檻，量出「誤拒答率」與「漏放幻覺率」。
3. **分路由逐步啟用**：先只對一個路由、一個政策開關啟用，觀察拒答率與告警，再擴大。
- 回滾：環境變數一鍵回到影子模式；新增欄位與表可保留。

## 6. 安全與隱私考量
- 檢索內容與使用者輸入一律視為**資料**，不當指令；提示詞中指令區與參考資料區分離（架構圖 Ollama 框內已要求）。
- 拒答佇列與風險標記含使用者問題文字，適用 Phase 3 的資料最少化、遮罩、保存期限與刪除規則；未滿足前置條件前不得寫入。
- 拒答訊息不得洩漏內部門檻、路由名稱或資料庫結構。
- 4c 的模糊檢索只查本地資料庫，不對外送出使用者問題。

## 7. 測試策略
- **單元**：三態判定的邊界（剛好等於門檻）、空檢索結果、各路由分數尺度；粗篩對已知洩漏指令字串；模糊命中的正規化與 K 邊界；政策開關的兩種行為。
- **校準／驗收**：黃金集上量測「誤拒答率」（有資料卻拒答）與「漏放幻覺率」（無依據卻放行）；以現有離線評測資料整理的已知幻覺案例做誤判率驗證（上位設計 §7）。
- **對抗**：提示注入內容混入檢索結果，確認不改變判定；超長答案、空答案、非中英文字元。
- **線上安全**：影子模式期間延遲 P50／P95 與開啟前比較；防護元件故障注入測試（逾時、拋例外）確認符合 §5.3。

## 8. 部署與運維
影子模式 → 校準 → 分路由啟用（§5.4）；`eval.alerts` 新增「拒答率 >15%」與「粗篩未過率上升」；每週人工抽樣拒答佇列。需重啟後端（約 10 秒）；Open WebUI 端無需改動（回應欄位為新增、舊 pipe 可忽略）。
