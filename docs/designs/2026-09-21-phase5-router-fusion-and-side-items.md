## 1. 背景與問題

架構圖中間的「Query 前處理 → RAG Router → 三個檢索庫 → 融合節點（RRF）→ Reranker」整條主幹，實況如下（已查證）：

| 圖上的元件 | 現況 |
|---|---|
| RAG Router（自動選路） | **沒有**。使用者（或 Open WebUI 的 pipe）用 `模型@策略` 指定策略；後端註冊 11 個策略 id。只有 `AgenticRAG._analyze_intent` 用幾個中文關鍵字（「關係」「影響」「是什麼」…）在內部挑向量或圖 |
| 融合節點（RRF） | **沒有系統級的**。只有 `HybridESRAG` 自己手動做 BM25＋向量的 RRF；`HybridBalancedRAG` 是「向量取一半、圖取一半」直接串接，**完全沒有分數融合** |
| Reranker（Cross-encoder） | **沒有**。圖檢索用「全文分數＋擴展豐富度加成」，其餘只依分數排序（見 Phase 4 §3） |
| 語意快取（Redis） | 後端用**記憶體內**的 `QueryCache`（1000 筆、TTL 1 小時；鍵為「查詢＋策略＋筆數」的精確比對）；Redis 在 6379 執行但後端沒有使用；資料更新後靠夜間流程呼叫 API 手動清快取 |

**不做會怎樣**：四種路由的優劣只能人工比較；每個策略各自為政、分數不可比，Phase 4 的證據門檻與 Phase 3 的路由比較都要各策略各校準一次，成本與誤差都高。

## 2. 目標與非目標

### 目標
1. **系統級融合**：把各檢索庫的候選以 RRF 融合成單一排序（取代各策略自己的排序邏輯）。
2. **真正的重排**：在融合後加入重排，讓「進 prompt 的 Top-N」有品質把關。
3. ~~**Router**：依查詢意圖與實驗層的量測結果，自動選擇路由；**改變路由權重必須經人工確認**，不自動生效。~~ **更正（2026-09-23）**：Router 不做自動判斷，改為**依請求指定**的 4 種策略（`vector`／`fulltext`／`graph`／`hybrid`，預設 `hybrid`）路由；見 §4.2、§4.3 更正與 §9
4. **實驗層**：依黃金集強制切換四種路由、依 `route_id` 分組比較，產出效果報表（Phase 3 的 `/api/v1/eval/routes/compare`）。

### 非目標
不改資料層（Phase 1／2 已完成）；不引入「自動調整系統參數」的機制（見 Phase 3 §3 對 `alert_and_optimization_system.py` 的結論）。

## 3. 現況與重用
- `HybridESRAG` 的手動 RRF：可抽出為共用函式（公式 `1/(rank+60)`，與架構圖一致）。
- `MultilingualQueryTranslator`、`SmartKeywordExtractor`：Query 前處理已有，可直接作為 Router 的輸入特徵。
- Phase 3 的 `evalrun` 與 trace 入口：實驗層的量測基礎；Phase 4 的分路由校準門檻。
- 模型：`bge-m3` 已安裝；**沒有**重排模型（cross-encoder）。

## 4. 方案比較

### 4.1 重排怎麼做
| | 方案 A：專用 cross-encoder（例如 bge-reranker 系列） | 方案 B：用 Ollama 的 LLM 對候選打分 | 方案 C：先不重排，只做 RRF |
|---|---|---|---|
| 品質 | 通常最好 | 中，且不穩定 | 基準 |
| 新增依賴 | 是（模型下載＋函式庫），**須做來源、授權、供應鏈評估**；GPU／記憶體需求待測 | 否 | 否 |
| 延遲 | 每個候選一次前向，Top-20 約數百毫秒（待實測） | 數秒以上 | 0 |
| **建議** | 若評估通過，用 Phase 3 量測比較 A 相對 C 是否**實質提升 nDCG** 才採用 | 不建議（慢、不穩） | **先做 C**（Phase 5 第一步），量出基準再決定是否加 A |

### 4.2 Router 怎麼決定
| | 方案 A：規則式（關鍵詞、實體偵測，延伸現有 `_analyze_intent`） | 方案 B：實驗層統計回饋 ＋ 規則式 | 方案 C：LLM 分類意圖 |
|---|---|---|---|
| 可重現、可解釋 | 是 | 是 | 否 |
| 延遲 | 幾乎 0 | 幾乎 0 | 多一次生成 |
| 依賴資料 | 無 | Phase 3 的路由比較數據 | 少 |
| **建議** | 第一步 | **第二步**（權重調整經人工確認後才寫入設定） | 不建議 |

現有 `_analyze_intent` 只有 6 個中文關鍵字、英文查詢幾乎全落入 `hybrid`，需先補強（多語、實體偵測）並用黃金集驗證。

> **更正（2026-09-23）**：上表與此段討論的是「規則式自動判斷該用哪一路」，**已由使用者裁定不採用**——Router 改為完全依請求指定的策略，不自動判斷（見 09-23 規格書 RET-01：「Router 依請求指定的策略路由（**不自動判斷**）」）。`_analyze_intent` 的補強、方案 B（實驗層統計回饋）與方案 C 皆不再是 Phase 5 的工作範圍。原因：規則式自動判斷需要額外的意圖分類邏輯與黃金集驗證，屬範圍擴張；且會讓 Phase 5 的驗收（RRF 融合是否優於單路）與自動選路的誤差混在一起，難以歸因退步是融合造成還是選路造成。詳見 §9。

### 4.3 收斂方式：新路徑與舊策略並存

> **更正（2026-09-23）**：本節提出的 `auto` 策略 id、與舊 11 個策略 id 並存觀察期的漸進上線計畫，**已隨 §4.2 的更正一併撤銷**。Phase 5 的工作範圍改為：既有 `hybrid` 策略內部改用系統級 RRF 融合（取代 `HybridESRAG`／`HybridBalancedRAG` 各自的手動邏輯），`vector`／`fulltext`／`graph` 三個單路策略不變；不新增策略 id，不需要與舊 11 個 id 並存的觀察期機制。下方原始討論保留存查。

上位設計已定：**保留舊路徑一段觀察期**。新增策略 id（例如 `auto`）走「Router → 融合 → 重排」，舊的 11 個策略 id 不動；Open WebUI 的模型清單可同時提供 `auto` 與原策略，由實驗層比較。確認 `auto` 在黃金集上不劣於最佳單一策略後，才把 `auto` 設為預設。

## 5. 系統設計（草案）
```
查詢 ► 前處理（改寫／翻譯／實體）► Router ► 選定的檢索庫子集（並行）
   ► 系統級 RRF 融合 ► （選用）重排 ► Top-N ► Phase 4 證據判定 ► 生成 …
```
- **設定驅動**：RRF 參數（`k` 預設 60）放設定檔（不寫死），變更留下版本與原因。
- **route_id**：即請求指定的策略（`vector`／`fulltext`／`graph`／`hybrid`），量測時依此分組；**不再有 `auto` 子路由**（見 §4.2／§4.3 更正）。
- **失敗降級**：某檢索庫逾時或失敗，融合略過該來源並標記 `partial_retrieval`，不讓整個查詢失敗。
- **回滾**：融合邏輯以設定開關一鍵退回舊的各策略手動邏輯（`HybridESRAG`／`HybridBalancedRAG`）。

## 6. 另案項目（各自獨立，皆非 Phase 5 的前置條件）

### 6.1 Redis 語意快取＋outbox 觸發失效
- **現況問題**：現有快取是精確字串比對（並非語意）；資料變更只能靠夜間流程整個清空；`optimization_manager.py` 的 `SmartCache` 不能沿用（無失效機制、連 Redis 未帶密碼，見 Phase 3 §3）。
- **選項**：
  - **A（建議先做）**：維持記憶體快取，但改為**以 outbox 事件精準失效**——訂閱 `catalog.sync_events`，只清除與變更文件有關的項目（或簡化為「有任何事件就清空」）。不引入 Redis，風險最小。
  - **B**：改用 Redis（多程序共享）並做語意近似比對（以 `bge-m3` 向量找相近查詢）。需要 Redis 密碼與存取控制、相似度門檻校準，且**語意快取可能把「相近但不同」的問題回成同一答案**，須用黃金集驗證。
- **前置**：與使用者身分無關（快取為全域，不含個資）；但**若快取答案，必須連同其證據狀態與風險標記一起快取**，且拒答結果不得被快取成「答案」。

### 6.2 嵌入模型「名稱＋版本」標註
- **現況**：ingest／訂閱器沒有任何欄位記錄向量由哪個模型與版本產生（已查證無 `embedding_model` 類欄位）。
- **風險**：日後換模型，新舊向量混在同一 collection 會讓檢索品質無聲劣化，且無法判斷哪些資料需要重嵌入。
- **建議**：在 chunk metadata 與 catalog 記錄 `embedding_model`、`embedding_version`；`ingest verify` 增加「版本一致」檢查。這是**小改動但涉及 schema／metadata 變更**，仍走 GD（不符合 CLAUDE.md §3 例外）。

### 6.3 每週全量一致性稽核
- **現況**：夜間流程已有 `ingest verify`（catalog 對三庫，全量比對計數與 id），只是**資訊性記錄**，沒有門檻告警、沒有趨勢。
- **建議**：不新增機制，只把 `verify` 的結果寫入 `eval.alerts`（不一致數 >0 即告警），並保留每週一次的深度比對（含內容雜湊抽樣）；圖上標示為「非主要更新路徑」，與現況吻合。

### 6.4 Google Books 後置補充查詢（圖上有、目前沒有，**尚無設計**）
- **現況**：架構圖在「生成模型」與「守門員」之間畫了 Google Books 後置補充；後端檢索端沒有任何呼叫，`crawlers/fetch_google_books.js` 只是離線爬進資料庫（來源名 `google_books`，目前 29 筆）。
- **選項**：A 不做，維持離線入庫；B 生成後只用**書目關鍵字**（書名、作者、ISBN）查 Google Books，補「延伸閱讀」，不送使用者原文；C 把使用者問題即時送 Google Books。
- **建議**：先不做（A）。若要做採 B，C 不建議：使用者問題會送到外部服務，與 Phase 3 §6 的「資料不出境」原則及開放多人使用後的隱私要求衝突。
- **若做 B 需另行評估**：外部服務的條款與配額（爬蟲已有 429 偶發）、金鑰保管、失敗降級（補充失敗不得影響主回答）、補充內容也必須經 Phase 4 的忠實度檢查，且要明確標示「來自外部補充」。

## 7. 測試策略
- **單元**：RRF 公式與並列處理、缺少某來源時的降級、Router 規則的邊界、設定變更版本記錄。
- **驗收**：黃金集上比較 `auto` 與四個單一策略的 Recall@K／nDCG@K；重排（若採用）相對純 RRF 的提升需**統計上可見**才採用。
- **線上安全**：新路徑先在影子模式（並行計算但不回傳）比較延遲與結果差異，再開放少量流量。

## 8. 部署與運維
系統級 RRF 融合先於 `hybrid` 策略內以影子模式並行計算（不回傳，只記錄與現行手動邏輯的差異）→ 比較 recall@n → 確認優於單路最佳後才正式取代現行 `HybridESRAG`／`HybridBalancedRAG` 的手動融合邏輯。需重啟後端；Open WebUI 端策略清單不變（`vector`／`fulltext`／`graph`／`hybrid` 四種，無需新增選項；見 §4.2／§4.3 更正）。
