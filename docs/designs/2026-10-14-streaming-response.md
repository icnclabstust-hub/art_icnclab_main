# 設計文件：回答改為串流顯示（首句：已載入 ≤ 3 秒、換載 ≤ 10 秒）

> 狀態：**使用者已確認（2026-10-14）**，實作於 8011；上線待指導老師核可（Tier B）。風險 Tier B（改變 Open WebUI 使用者路徑）。
> 依據：2026-10-14 E14——完整回答 ≤5 秒 0／15（生成本身 5～100 秒）；串流首字（模型已載入）0.2～0.6 秒。

## 1. 問題
pipe 呼叫 `/api/v1/query`（`stream: False`），使用者要等**整段回答**生成完才看到任何字：8B 模型熱查詢中位 7.6～16 秒、gemma4:12b 約 100 秒、qwen3:14b 約 50 秒。生成速度受 8 GB GPU 限制（8B 約 60 tok/s；12B／14B 部分在 CPU，7～14 tok/s），縮短完整回答時間只能靠縮短答案，會犧牲內容。

## 2. 目標與非目標
- 目標（使用者 2026-10-14）：首句出現時間 **模型已載入 ≤ 3 秒、換載模型 ≤ 10 秒**（8B 模型）。
- gemma4:12b／qwen3:14b 受 8 GB VRAM 限制達不到（見 decision-log 同日「硬體限制」），標示「深度思考／較慢」並提示預估等待。
- 非目標：不縮短完整回答時間；不改檢索、提示詞、模型。

## 3. 方案
### 3.1 後端：新增 `POST /api/v1/query/stream`（`/api/v1/query` 不變，評估腳本照用）
- 請求格式同 `/query`。回應 NDJSON（每行一個 JSON）：
  - `{"type":"meta", "sources":[...], "citations":[...], "translation":{...}}`（檢索完立刻送）
  - `{"type":"delta", "text":"…"}`（生成中逐段送，Ollama `stream: true`）
  - `{"type":"done", "metadata":{...}}`（含時間、guard 結果）
- 答案快取命中：直接送 `meta`＋一個完整 `delta`＋`done`。
- **生成完成後**才做：寫入答案快取（拒答不快取 RET-13 不變）、守門員影子模式（GRD-06／08 不變）。
- deepseek-r1 會把 `<think>…</think>` 寫進回應：串流時以狀態機略過該段（未閉合到結束則丟棄，同 `_clean_translation` 的規則）。
- 失敗：生成中斷時送 `{"type":"error"}`；pipe 顯示已收到的內容＋錯誤註記。

### 3.2 Open WebUI pipe（8 支 system／legacy pipe 共用邏輯）
- `pipe()` 改回傳 generator（Open WebUI 支援 pipe 串流），閥值 `STREAM=True`（預設開；關閉＝現行非串流）。
- **OpenCC 簡轉繁**：逐段轉換會切斷詞（「软件」跨兩段轉不成「軟體」）→ 緩衝到標點或換行再轉換送出（延遲 < 1 句）。
- 參考來源清單與「知識庫無資料」提示：在 `done` 後附加（同現行格式）。
- 串流端點失敗（連線錯誤、404）：自動退回呼叫 `/api/v1/query`。

### 3.3 整句送出與檢查點（架構接點）
- 後端以句為單位送 `delta`（句號、問號、驚嘆號、換行、分號；中英文皆可），每句先經 `sentence_hook(sentence, sources) -> sentence | None` 再送出。
- 現在 hook 為 no-op（守門員仍是影子模式，於 `done` 後整段計算）；守門員改攔截（#15）或分層回答（#12）時接在 hook，不需重做串流。
- 代價：多等一句（8B 約 0.5 秒；12B／14B 約 2～4 秒）。OpenCC 與 `<think>` 過濾同在句緩衝處理。

### 3.4 並行預載與狀態列
- 收到請求即對 GPU Ollama 送預載（只載模型、不生成），與翻譯、檢索並行；換載時省 1.5～2 秒。開關 `GENERATION_PRELOAD`（預設關）。
- pipe 在檢索前以 Open WebUI 狀態事件顯示「🔎 正在檢索…」，大模型另顯示「深度思考模式，預估 15～30 秒開始回答」。狀態列不計入首字時間。

### 3.5 架構接點檢查（四層）
| 層 | 接點 | 影響與處理 |
|---|---|---|
| 1 | Open WebUI ↔ pipe ↔ 後端 | 新端點；`/query` 保留 |
| 1 | Redis 答案快取 | 結束後寫入，拒答不快取不變；命中時一次送完整答案 |
| 1 | 8080 評估（Open WebUI API 非串流呼叫） | 需實測 Open WebUI 是否把 generator 拼成完整回答；不行則評估改串流讀取 |
| 2 | 翻譯、檢索、RRF、證據判定／K | 皆在生成前，不受影響 |
| 2 | 守門員（#15）、分層回答（#12） | 生成後處理與串流衝突（已顯示的文字收不回）→ 整句檢查點 |
| 3 | catalog、outbox、快取失效 | 無影響 |
| 4 | 四段式量測、guard_shadow、評估 | `done` 附完整回答與各階段時間（新增首字時間），8080 評估加串流模式 |

### 3.6 不做的替代方案
- 只設 `RAG_MAX_TOKENS_CAP` 縮短答案：完整回答仍 ≥ 5 秒（llama 熱查詢最短 5.2 秒），且犧牲理論題內容。
- 前端假進度條：不改善實際等待。

## 4. 驗收
- 8011：5 模型 × 熱／冷，量首字時間與完整時間；與 `/query` 比對答案內容一致（同溫度 0 時逐字相同）。
- 單元測試：think 段過濾（閉合、未閉合、跨 chunk）、OpenCC 緩衝（跨 chunk 詞）、快取命中路徑、錯誤路徑。
- 上線後 8080：首字 ≤ 5 秒的比例（模型已載入），完整回答品質不變。

## 5. 部署與回退
